# 五个维度的页面评审

以下是通用启发式，不是团队硬规范。先看实际设计与核心任务，再选择适用检查项。差异可能服务于不同任务、状态或平台，不要求所有页面相同。不得为凑数量制造问题。

## 1. 页面框架合理性

判断页面内容组织是否支持用户完成主要任务。

- 信息分组与顺序是否符合用户理解和决策过程；模块边界是否清楚。
- 主任务、关键内容与主要操作是否有可识别的优先级；次要内容是否造成竞争。
- 导航、当前位置、返回路径是否符合页面层级；跨页任务是否连贯。
- 标题、规则、费用及操作后果是否出现在需要作决策的位置。
- 只有证据支持时才判断首屏、滚动、固定操作区、适配和遮挡；截图裁切不等于实际内容缺失。

建议应明确模块调整、分组或顺序，以及对任务的帮助，不因个人喜好要求重做布局。

## 2. 视觉一致性

判断视觉语言是否连贯，差异是否能表达正确的层级和语义。

- 同级标题、正文、辅助说明的字重与视觉层级是否一致、可读。
- 同类模块的间距节奏、对齐关系、容器、图标风格是否存在无理由的差异。
- 强调色、状态色、弱化样式的语义是否稳定；是否只靠颜色传达关键状态。
- 图文密度与装饰是否干扰关键信息，选中、禁用等状态是否易区分。
- 跨页、日夜间模式或平台间的对比仅限实际提供的材料，并允许合理适配。

截图可支持可见差异，不能直接证明精确色值、字号、对比度或 token 绑定错误。精确结论需要节点数据或可靠测量。

## 3. 组件一致性

判断同类任务与状态是否使用稳定的组件语义。

- 同类按钮、输入框、标签、列表、卡片、弹窗的结构和操作规则是否一致。
- 主次、危险、禁用、加载、选中等变体是否符合当前任务和已提供的组件规范。
- 相同行为的图标、文案、点击区域表达是否一致；不同操作是否被误做成相同语义。
- 组件内部的标题、说明、状态、操作等槽位安排是否稳定；差异是否有业务理由。
- 有组件库资料时对照名称、变体和使用条件；有节点证据时才判断实例、绑定或脱离组件。

没有组件库也可比较可见结构与语义，但不能声称“没有复用组件”。建议同时指出差异组件和可参照对象；无可靠参照时描述应统一的行为或结构。

## 4. 交互合理性

判断操作是否可发现、结果是否可预期，以及用户能否继续或恢复任务。

- 入口、操作文案与结果是否匹配；当前状态、进度、操作后果是否清楚。
- 返回、取消、关闭、撤销是否符合场景；高影响操作是否有适当的防误触与恢复方式。
- 输入格式、校验时机、错误提示位置与修正路径是否有助于完成任务。
- 按场景检查加载、重复提交、空内容、失败、权限及成功反馈，不要求所有页面具备全部状态。
- 有可操作原型时按入口→操作→反馈→返回／恢复验证；键盘、焦点与辅助功能需对应可运行证据。

静态稿只能检查可见线索和已标注规则。未展示状态先列待确认；不得断言点击无效或功能不存在。修改建议写清触发条件、反馈与恢复路径。

## 5. 体验优化空间

判断是否存在有价值、可解释的任务成本改善机会。

- 可否减少重复输入、无效跳转、重复确认或不必要的操作步骤。
- 是否能通过就近说明、清晰文案、信息汇总降低记忆和理解负担。
- 默认值、历史记录、批量操作、渐进展示等是否适合当前频次和风险，避免无条件引入。
- 长内容、边界值和不同熟练程度的用户是否会遇到明显障碍。
- 优化是否损害信息透明、可控性、误操作防护或必要业务约束。

区分缺陷与优化机会。写明适用用户／场景、预期减少的成本和取舍；无数据时不声称能提高某个百分比的转化率。

## 覆盖与证据

报告逐维度记录检查范围、结论和限制。可用结论为“发现问题／本轮未发现有充分依据的问题／证据不足／不适用”；没有问题不等于证明体验完善。

需求覆盖有独立证据时记录；没有需求时不虚构完整覆盖。可访问性、文案、状态和交付说明按对应维度检查，不另造重复问题。

## 意见校准示例

- 可定位且可执行：订单确认页 screenshot-02 的底部操作区，“返回修改”与“提交订单”同样强调。若提交为主要任务，建议突出提交、弱化返回但保留可发现性；通过任务测试确认主操作识别是否更顺畅。无团队规则或测试时标潜在风险。
- 跨页一致性：同时列出 A 页和 B 页的卡片、具体差异和实际参照；先确认它们的任务与状态可比，再建议统一对应槽位或变体。
- 待确认：仅看到订单默认态，无法确认失败恢复；请求失败状态稿或交互说明，不写“缺少失败页”。
- 不可用：“按钮改成蓝色”“圆角统一 12px”“优化层级”。缺少依据、定位或具体行动。
- 复审：新图新增了后果提示，但完整文案不可见，应标部分解决或无法确认，不能仅因有提示框就判为已解决。
